# 20 · 风险字段与学校规则

> 证据等级：**A**（源码/实测）+ **C**（学校与社区口径，逐条标注）
> 最后更新：2026-11-11 · 对应版本 **0.2.2**

## 1. 先记住结论

**`policy` 不是风险标记。** 它是服务器下发的**规则集编号**（`1` = 学分跑），
详情接口会原样回显。旧版前端（0.2.1 及以前）把所有非零 `policy` 当成反作弊标记，
所以 11/05 之后正常的学分跑记录也被画成红色（issue #14）。

**真正的风险字段**：

| 字段 | 含义 | 出现位置 |
|---|---|---|
| `isCheat` | 服务端反作弊命中，`1` = 异常 | 记录详情 |
| `stepFreqStatus` | 步频异常标记，非 0 = 异常 | 记录详情 |
| `status` / `status_code` | 记录状态；`1` / `2` 视为有问题 | 列表 / 详情 |
| `normalRun` | `false` = 非正常跑 | 列表 |
| `reasonList[].complete` | 原因项是否完成；有未完成项 = 有问题 | 详情 |
| `reasonList[].reason` | 服务端给出的原因文本 | 详情 |

依据：`app/frontend/js/app.js::recordState()`、`selectRecord()`；
`app/replica/application/readonly.py` 的详情映射；
`docs/decisions.md` §25。

## 2. `policy` 到底是什么

`runModePolicy` 的 `operateType`：

| 值 | 返回 | 用途 |
|---|---|---|
| `0` | 只返回 `policy` | 开始跑步 |
| `1` | 返回 `runRuleModel` | 学期视图 / 设置页读取学校规则 |

- 提交体的 `policy` / `selDistance` 取自服务器，不是本地随便填。
- `policy=1` 表示当前走的是**学分跑规则集**，不代表账号被标记。
- 详情页现在把它单独显示为「规则集 policy=1」，并带 tooltip 说明。

> 判断记录是否异常，不要看 `policy`；看 `isCheat`、`stepFreqStatus`、`status`、
> `normalRun` 和 `reasonList`。

## 3. 学校规则（因校而异）

「运动世界校园」的合格条件由学校在后台配置，常见维度：

| 维度 | 典型口径 | 证据 |
|---|---|---|
| 最低距离 | 男生 2.0 km / 女生 1.5 km | C（多校通知） |
| 配速区间 | 2'11"–10'00"/km；也有学校写 3–10 分/km | C（2019 校级指南；2026 聚合页） |
| 步频 | 有的写 8–40 不通过，有的写 60–300 合理 | C（互相冲突，见 §4） |
| 有效时段 | 06:30–22:00；也有学校拆成多段 | A（服务器 `runRuleModel`）+ C |
| 打卡点 | 必须经过指定绿色/蓝色点 | C（校级指南） |
| 围栏 | 必须在校区围栏内 | A（接口） |
| 每日次数 | 学校单独限制 | A（服务器记录）+ C |

**以服务器返回的 `runRuleModel` 为准**。设置页「从服务器读取」必须用
`operateType=1`，否则只能拿到 `policy`。

## 4. 社区口径为什么互相冲突

| 说法 | 来源 | 判断 |
|---|---|---|
| 步频 8–40 不予通过 | 百度聚合页（2026） | C，可能是某校/某版本 |
| 步频合理区间 60–300 | 应用下载站（旧版说明） | C，和上一条明显冲突 |
| 配速 2'11"–10'/km | 2019 校级使用指南 | C，年份早，规则可能已变 |
| 配速 3–10 分/km | 2026 聚合页 | C，仍是“常见范围”不是平台常量 |
| 配速太慢不计入 | 多校通知 | C，各校阈值不同 |

**不要把这些数字写死到代码里当平台规则。** 它们只适合做提示文案或默认值，
真正判定要用服务器 `runRuleModel` 和提交后的详情。

## 5. 会不会被“清算”

- 服务端反作弊是**回溯性**的：今天自查正常，不代表上周的记录以后不会被复核。
- `policy=1` 本身不代表异常；`isCheat=1` / `stepFreqStatus≠0` / `status` 异常
  才是明确信号。
- 学校后台可以看到配速、步频、跑步模式、作弊原因和原因详情（C 级，知乎分析
  引用的管理后台截图）。
- 工具只能做**提交前提醒**和**提交后只读回查**，不能保证服务端最终判定。
- 回复用户时不要承诺“不会清算”，也不要把 `policy=1` 说成风险。

## 6. 工具里的对应实现

| 功能 | 位置 | 行为 |
|---|---|---|
| 提交前风险提醒 | `app/replica/application/riskcheck.py` | IP 城市 / 校园城市、有效时段、设备城市一致性；只 warn 不硬拦 |
| 合格性模型 | `app/replica/application/qualification.py` | 距离、配速、步频、点位、围栏等本地预检 |
| 记录状态 | `app/frontend/js/app.js::recordState()` | `normalRun` / `status` / 原因列表 |
| 详情风险 | `app/frontend/js/app.js::selectRecord()` | 只读 `is_cheat` / `step_freq_status` |
| 违规自查 | `api/v78/cheat/cheatlist` | 只读拉取 |
| 只读对账 | `docs/operations.md` §4 | 不重新提交，只核对回执 |

## 7. 回复 issue 的标准口径

1. `policy=1` 是规则集编号，不是风险标记；0.2.2 已修 UI。
2. 真实风险字段是 `isCheat` / `stepFreqStatus` / `status` / `normalRun` / `reasonList`。
3. 列表“已通过”和详情“风险标记”之前不一致，是前端展示 bug，不是记录状态变了。
4. 是否清算由平台决定，服务端反作弊回溯，软件显示只能参考。
5. 如果 `isCheat=1` 或 `stepFreqStatus≠0`，再按服务端原因列表分析。
